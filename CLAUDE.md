# Koala Budget — Claude Code Context

## Architecture

**Stack:** Django 6 (Python 3.12) backend · Django REST Framework · PostgreSQL 17 · Celery + Redis · React 19 + Alpine.js frontend · Tailwind CSS 4 + DaisyUI 5 · Vite 7 · TypeScript 5 · Playwright E2E tests

**Folder layout:**
```
apps/              # 19 Django apps (accounts, journal, budget, bank_feed, plaid, chat, ai, teams, users, …)
assets/javascript/ # React/Alpine.js components embedded in Django templates
frontend/          # Standalone React SPA (auth flows only)
templates/         # Django server-rendered templates
api-client/        # Auto-generated TypeScript API client (from OpenAPI schema)
e2e/               # Playwright + pytest E2E tests (Page Object Model)
docs/              # Developer documentation
context/           # context/CLAUDE.md — detailed LLM reference guide
deploy/            # Docker Compose and DigitalOcean configs
```

**Key modules:**
| App | Responsibility |
|-----|---------------|
| `accounts` | Chart of accounts — Account, AccountGroup, Payee, Institution |
| `journal` | Double-entry bookkeeping — JournalEntry, JournalLine |
| `budget` | Monthly budgets and savings goals — Budget, Goal, GoalAllocation |
| `bank_feed` | Transaction import staging — BankTransaction |
| `plaid` | Plaid live-sync integration — PlaidItem, PlaidAccount |
| `chat` / `ai` | AI chat interface and pydantic-ai agents |
| `teams` | People and billing — Team, Membership, Invitation |
| `books` | The money tenant — Book (a set of books), request plumbing, legacy redirect, book settings |
| `users` | Custom user model, avatars, preferences |
| `api` | API key auth — UserAPIKey, hybrid permissions |
| `subscriptions` | Stripe billing via dj-stripe |
| `reports` | Income statements, balance sheets, Sankey diagrams |

**Account number convention:** 1000s = assets · 2000s = liabilities · 3000s = equity/goals · 4000s = income · 5000s = expenses

**URL pattern:** `/a/{team_slug}/{book_slug}/{app}/{path}/` for everything in a set of books; team-level pages (members, subscription, team settings, `books/`) stay at `/a/{team_slug}/…`

## Conventions

**Python:**
- Double quotes, 4-space indent, 120-char line limit (Ruff enforced)
- All financial models extend `BaseBookModel` (`apps.books.models`) — a `book` FK, no `team` column
- Custom querysets for complex queries (e.g. `GoalQuerySet.with_progress()`)
- Book-scoped manager: `Model.for_book.all()` auto-filters by the current book (`STRICT_BOOK_CONTEXT` raises without one)
- Book views use `@login_and_book_required` or `@book_admin_required` and take `(request, team_slug, book_slug, ...)`; team-level views keep `@login_and_team_required`
- DRF ViewSets with `BookModelAccessPermissions` for book-scoped API endpoints
- `unique_together = ["book", "field"]` on book-scoped unique fields
- Reverse book URLs with both slugs: `reverse(name, args=book.url_args)` / `{% url 'x:y' request.team.slug request.book.slug %}`; the frontend builds from the `book-base` value (`common/book.js`)
- Amounts: `Decimal(max_digits=15, decimal_places=2)`, positive = outflow

**TypeScript/React:**
- 2-space indent, single quotes, semicolons
- Functional components with hooks
- Auto-generated API client from OpenAPI schema — never hand-write fetch calls
- Components self-mount via `document.getElementById('id').render(<Component />)`
- Props passed via `window.COMPONENT_PROPS` JavaScript variable

**Django templates:**
- 2-space indent
- Always use `{% translate %}` or `{% blocktranslate trimmed %}`
- Vite assets via `{% vite_asset 'path/to/asset.tsx' %}`

**Testing:**
- Backend: Django `TestCase` with `setUpTestData()` class fixtures
- E2E: Playwright POM pattern — page objects in `e2e/pages/`, tests in `e2e/tests/`
- Run: `make test` (backend) · `make test-e2e` (E2E)
- Coverage threshold: 50% minimum

- Bank feed: transfer mirror legs. Categorizing a bank transaction as a transfer to another **feed** asset/liability account (e.g. checking → credit card) now surfaces the transfer in *both* account feeds. `apps/bank_feed/services/transfer_mirror.py::sync_transfer()` creates/moves/removes a linked "mirror" `BankTransaction` (new `is_transfer_mirror` flag, `source=system`) in the counterpart account pointing at the **same** `JournalEntry` with the opposite-signed amount — so there's one entry (no double-count), the mirror shows in the counterpart feed via the existing per-account query (no feed/frontend change), and the two legs reconcile independently (per-`JournalLine` `is_reconciled`). `sync_transfer` is idempotent and symmetric, and runs from every categorization/edit path (`_create_journal_from_bank_transaction`, manual `create`, `update`, `_update_journal_category`, `batch_edit`, CSV `_auto_categorize_transaction`): it creates the mirror on first categorization, keeps date/amount/description/payee in lockstep when either leg is edited, removes the mirror if re-categorized away from a transfer, and — **fully transversable** — re-pointing *either* leg's category to another feed account moves the counterpart leg to follow (editing the mirror relocates the primary, and vice-versa). The one guarded case: pointing the **mirror** leg at a non-feed category (e.g. an expense) would orphan the real primary, so `would_orphan_primary()` makes `update`/`batch_edit` reject it with "edit the original transaction instead". `batch_delete` removes both legs + the shared entry; `find_transfer_candidates` skips two legs that share an entry so a primary+mirror is never flagged as a duplicate. Only mirrors targets with `has_feed=True` (expense/income categories never mirror).

- Transactions: per-column filters and sorting on the journal/transactions table. Every column header carries a chevron (`assets/javascript/transactions/ColumnMenu.jsx`) opening a menu with per-column sort options, a search box and a checkbox list of that column's **distinct values with row counts**; clicking the header label itself cycles the sort ascending → descending → back to the default newest-first. **All of it runs server-side**, because the table pages in as the user scrolls (`IntersectionObserver` + `next`) — a list of values built from the loaded rows would offer the first page's payees and quietly pretend the rest of the ledger had none. `apps/journal/filters.py` is the single definition of what a column *is*: `COLUMNS` maps each wire key (`date`, `payee`, `description`, `debit_account`, `credit_account`, `amount`, `source`, `status`) to the field it reads, and each carries the annotations it needs — `debit_account_name`/`credit_account_name`/`amount_value` are scalar `Subquery`s over the entry's two lines, ordered `("-dr_amount", "pk")` and `("dr_amount", "-pk")` so they reproduce exactly what `TransactionRowSerializer` shows, the $0.00 entry (every amount zero, split decided by line order) included. `line_count` moved from `Count("lines")` to a scalar subquery too: an aggregate forces a GROUP BY that the facet counts would then have to group again. `TransactionViewSet` gains `?f_<column>=` (repeated once per selected value; an empty value selects rows with **nothing** in that column, e.g. no payee) and `?sort=&dir=`, plus `GET transactions/facets/?column=&q=` returning `{values: [{value, label, count}], truncated}`. - Transactions: hierarchical column filters. - YNAB import: a migrating user drops their two YNAB export CSVs into an empty team and gets the whole budget — chart of accounts, five years of transactions, per-month budgets, savings goals and opening balances — with nothing left to categorise. New `apps.ynab_import` (plan: `docs/ynab-import-plan.md`, whose every figure was measured against the real export in `docs/reference/`). **Parsing and inference are pure** (`services/parse.py`, `analyse.py`, `build.py`): the preview screens and the apply step call the same `build(analysis, choices)`, so what the user reviews cannot drift from what is written. `apply.py` is one `transaction.atomic` block of inserts that decides nothing. What the export does not contain, and how each is recovered: **account type** (a card named by the Plan's `Credit Card Payments` group, then a balance that is never positive, then a negative starting balance — 6 liabilities / 30 assets on the sample, all correct); **on-budget vs tracking** (whether any row carries a category — 22/14); **what an inflow was** (YNAB gives every deposit the one category `Inflow: Ready to Assign`, so the 43 payees are clustered into income accounts on a wizard screen, with bookkeeping payees markable "not income"); **savings** (a `Savings` category funded by transfers becomes a `Goal` with its allocations, since an asset-to-asset move cannot post to a spending category without misstating net worth). Two rules earn their own note. **D2's top-up:** YNAB resets a negative `Available` to zero at the month boundary out of Ready to Assign while KB carries it forward, so importing `Assigned` verbatim would leave 31 of 45 categories deeply in the red; `budget_amount = Assigned + max(0, -PrevAvailable)` records the money that actually went in and reproduces YNAB's `Available` on all 2,610 category-months. **D1's back-fill:** each income account's budget is set to that month's own actual, so income `Available` starts at 0 rather than counting every dollar ever earned as a surplus. `reconcile.py` is the integrity gate and runs *before* anything is written as well as after: category activity, every category's `Available`, and each account's closing balance, all against the Plan's own columns (the sample passes 2,394 + 2,320 + 36). Transfers pair one-to-one (839, 0 unmatched), splits group by walking `Split (i/n)` in file order (83 groups, including the three whose transfer leg merges into the split rather than becoming its own entry), and `assert_sound()` refuses a plan where any row reached no entry. The apply runs as a Celery task with progress (6,623 entries + 13,335 lines in ~2s); `JournalLine.objects.bulk_create_for_import` resolves `budget_id` from an in-memory map because `save()` costs a query per line — and `bulk_create` skipping the audit signals is deliberate, with the one `AuditEvent.YNAB_IMPORT` as the record. Entry points, both: a "Coming from YNAB?" branch on the onboarding takeover (which **skips the questionnaire**, since the export answers it better — `complete()` straight to the `tasks` phase with import/categorize/budget already ticked) and a standalone wizard at `/a/{slug}/ynab-import/`, offered from the dashboard's "Finish setting up" card while the team is still empty. Frontend: Vite entry `ynab-import-app`, six screens over daisyUI (`assets/javascript/ynab_import/`). Three consequences worth knowing: a savings category with as much taken out as ever went in is *not* imported as a goal (the house was bought — a goal reading "$20,464 still to save" would be worse than none), every imported goal arrives funded with its quick-assign disabled until the target is raised, and a categorised transfer to a non-savings category keeps the movement but drops the category, which the reconciliation subtracts and the summary names.

- YNAB import: the apply screen tells the truth about a job it cannot see. Three faults fixed together. (1) **Progress was invisible while it mattered**: the import is one `transaction.atomic` block, so the `progress` the task wrote to its own row could not be read by the polling web process until the whole import committed — the bar sat at zero and then jumped. `services/progress.py::ProgressChannel` writes it on a **second database connection**, outside that transaction, alongside the existing Celery result-backend report; the two fail independently, neither may fail the import, and the channel sets `lock_timeout` so reporting can never wait on a lock the import itself holds. (2) **A dead worker showed a full bar forever**: `celery_progress` reports 100% for any *finished* task, success or failure, and `api_status` merged that number while the row still said `running` — so a worker killed mid-import (an out-of-memory container, a deploy) left the wizard full and waiting for something that was never coming. Live progress is now clamped to 99 while running, and a task Celery calls complete whose row has gone quiet past a grace period is reported as failed, with the reassurance that one atomic block earns: nothing was written. (3) **No sense of time**: `YnabImport.started_at` plus derived `elapsed_seconds`/`eta_seconds` (silent below 10%, where the opening phase's rate says nothing about the rest) feed a coarse "under a minute left" on the screen, and `Step6Apply.jsx` keeps the bar monotonic and creeping gently between the server's phase reports so a long silent phase never looks like a hang. A queued import that nothing has picked up says so after 12 seconds, naming the background worker — the likeliest reason a fresh environment sits still.

- YNAB import: the import outlives the browser, so the page can answer what happened while it was gone. - Bank feed / Transactions: **split transactions** — one bank transaction apportioned across several categories (plan: `docs/split-transactions-plan.md`). The shape is the one `apps.ynab_import` already builds: **one line on the bank account carrying the total, one counter line per leg**, so an imported split and one made in the UI are the same thing, and **no migration was needed** — `JournalEntry`/`JournalLine` already expressed it and the API already validated >=2 balanced lines. New `apps/bank_feed/services/splits.py` is now the single place a feed transaction's journal lines are written (a plain transaction is a split with one leg), holding the sign convention — *a leg takes the same side as its own sign; the bank line takes the opposite side of the total*, which balances for any mix including a refund leg inside an outflow and a gross paycheque with deductions — plus `parse_legs` (team-scoped account lookup, 2–20 legs, no zero amounts) and `check_legs_total`. The bank line is **updated in place, never recreated**, because it carries `is_reconciled`/`is_cleared` and recreating it would silently unreconcile a confirmed transaction; for the same reason `JournalEntrySerializer.update()` (which deletes and recreates all lines) must not be used on this path. **Splits already existed in user data and five things assumed two lines.** Measured against the unfixed code, opening a split in the feed modal and saving it returned HTTP 200 and left the ledger out by the transaction's full amount — both legs collapsed onto one account at `dr=210.40` against a bank line of `cr=210.40`, debits 420.80 vs credits 210.40, uncaught because `JournalEntry.clean()` is never called on that path. The others: `bank_transaction_to_feed_row()` had no `break` in its category loop so a split reported whichever leg sorted last as its one category; `_update_journal_category()` re-pointed only the first leg, so a bulk categorize left a split balanced and quietly wrong; `sync_transfer()` took the first non-bank line as the counterpart, so a split whose first leg was a feed account grew a phantom mirror row for the split's whole amount; and the reconciled-category guard fired on any request without a single category, which a split never has. Bulk paths now **refuse** splits (checked before the loop, so one split in a select-all cannot half-apply the batch) and collapsing one requires an explicit `remove_split` flag rather than being implied by a payload that omits `splits`. **Re-apportioning a reconciled split is allowed** — reconciliation is a fact about the bank line, whose amount does not change — while changing its total is refused. Read side: feed rows gain `is_split`/`split_count`/`splits` and report `category: null` for a split; `TransactionViewSet` **dropped its `.filter(line_count=2)`**, which had been silently hiding every split from the page that presents itself as the ledger (and from its filters, facet counts and export), and `TransactionRowSerializer` reports `Split (N)` on whichever side carries several lines plus `line_count`/`is_split`/`legs`. Frontend: `SplitEditor.jsx` (leg table, seeded with the full total on the first leg so `Remaining` starts at `$0.00` and goes negative as you over-assign; clicking the shortfall assigns it) inside `EditTransactionModal`, which grows to `size="lg"` in split mode; Save is disabled while unbalanced, and amounts are `type="text"` parsed by the shared `common/amount.js` (`sanitizeAmount` moved out of `BudgetGrid.jsx`, so the grid and the editor cannot drift). - Data portability: a team's whole books download as one file and load into another team. New `apps.portability` (plan: `docs/export-import-plan.md`), reachable at `/a/{slug}/data/` from the Settings rail. **The format is three CSVs and a manifest in a zip, not a model dump** — `accounts.csv` (one row per `Account`, with `AccountGroup`, `Institution` and `Goal` folded in as columns, since each is either unique-by-name within the team or backed one-to-one by the account), `journal.csv` (one row per `JournalLine` with the entry's columns repeated, plus `feed_*` columns carrying the row's `BankTransaction`), `budget.csv` (one row per monthly amount, `Budget` or `GoalAllocation`, told apart by a `kind` column). `services/schema.py` is the single source of truth **and both directions are generated from it** — `export.py` never names a field (it calls `schema.build_row((ACCOUNT, account), (ACCOUNT_GROUP, account.account_group), …)`) and `apply.py` never names one either (`Account(team=…, account_group_id=…, **schema.model_kwargs(schema.ACCOUNT, row, skip={'id'}))`), so **adding a field is an edit to one declaration plus its file's column tuple**, not to three hand-written blocks that could drift. A `FieldMap` per model names every concrete field as either a column or a documented omission, and `test_schema.py` walks `model._meta.get_fields()` against both halves in both directions, so a field that belongs to neither — or a `FieldMap` naming a field the model no longer has — fails a test instead of silently not travelling. A `ColumnSpec` covers the three cases plain attribute access cannot: `read=` (an FK carried as a name or a bare id), `absent=` (what the column holds when the object is not there — the default is whatever a blank cell decodes back into, so a row built from instances and the same row read from a file agree), and `writes=False` (another map in the same row already writes this column). `ROW_COMPOSITIONS` declares which maps make up one row of each file, and the tests check every map belongs to a composition, no two maps in a row write the same column, and no column is left with no writer. `docs/export-import-plan.md` §10 is the how-to-change-this recipe. That test earned itself twice before the code existed — the plan's hand-written column tables had missed `goal_archived_at`, `BankTransaction.amount`, and `is_archived`/`archived_at` on **all ten** models (they come from `BaseModel`, not from any model's own declaration, so reading declared fields misses them; the visible consequence would have been un-archiving every archived feed row on import). **Bank-feed rows are carried, never inferred**: `JournalEntry.source` cannot identify feed origin — `bank_feed/views.py` writes `SOURCE_MANUAL` on real feed rows, and the YNAB importer writes `SOURCE_IMPORT` on thousands of entries with no feed row at all — so an uncategorized feed row travels as a `journal.csv` line with a file-level `status=uncategorized` sentinel and a blank `entry_id`. Ids in the files are internal references only (they are remapped on import), because `Account` has no name-uniqueness constraint, so names cannot be handles. The import is **replace, never merge**: `services/wipe.py` clears the team first (`_raw_delete` for lines and entries to skip the audit `post_delete` signals on what can be tens of thousands of rows, then one `Account.delete()` cascade whose returned breakdown *is* the count — `QuerySet.delete()` reports exactly, so nothing is inferred), and `services/apply.py` runs read → wipe → insert → verify in one `transaction.atomic`, with a `_verify()` gate that re-derives net worth, trial balance and per-account balances from what was written and rolls the whole thing back on a mismatch. **The safety export is taken deliberately *outside* that transaction** — inside, a rollback would destroy the backup that exists to survive that exact rollback. Malformed archives are refused at *upload*, before anything is written, with a message naming the file, row and column (`journal.csv, row 2, column 'dr_amount': 'eighty-four' is not a valid amount.`). Export is open to any member; every import endpoint is `@team_admin_required`, and the confirm step re-checks the typed team name server-side. Frontend: Vite entry `data-transfer-app`, a four-step wizard whose apply screen reuses the YNAB importer's progress-bar rules (`Step6Apply.jsx`) rather than reinventing them. **`ProgressChannel` is shared**: `apps/utils/progress.py` holds the one copy (a second database connection so a row's `progress` is readable while the import's transaction is still open, plus the lock timeout that stops the reporter deadlocking against the thing it reports on), with a thin model-binding subclass in each of `apps.portability` and `apps.ynab_import` — which had byte-identical copies of it apart from a log message. **Splits need nothing special and are tested for it**: a split is one entry with a bank line plus a leg per category, so it is simply 3+ rows sharing an `entry_id` — the exporter iterates lines, the balance check sums per entry, and the importer groups by `entry_id`. The two places a two-line assumption would have bitten are covered: the feed row is looked up by `(entry_id, account_id)` so it lands on the bank line and not on every leg, and `feed_is_mirror` is carried rather than re-derived, so a split can never grow the phantom mirror that calling `sync_transfer` on it would create. Two traps worth keeping: a Playwright page object must not wait for the upload `<input>` to be *visible* (it is deliberately `.hidden` behind a dropzone button — wait for the dropzone, address the input as `state="attached"`), and a second team created inside an E2E test needs an `OnboardingState` marked finished or `team_home` redirects the assertion into the onboarding takeover.

## Agent Notes

This repo uses a six-agent AI pipeline for feature development. The pipeline is defined in `.claude/workflows/feature-pipeline.md`. Agent system prompts live in `.claude/agents/`.

**Pipeline order:** Designer → Feature Engineer → QA/Tester → Documentation Updater → Security Reviewer → PR Creator

**Stop conditions:**
- QA No-Go → return to Feature Engineer with bug list
- Security Blocked → return to Feature Engineer with Critical/High findings

**Living documents agents read/update:**
- `CLAUDE.md` (this file) — architecture, conventions, recent changes
- `docs/design-document.md` — UI/UX decisions
- `docs/testing-guide.md` — test patterns and coverage
- `docs/security-log.md` — security findings log

**Key pattern for new features:** Always extend `BaseBookModel`, always add `BookModelAccessPermissions`, add each new book URL to the isolation tables in `apps/books/tests/test_isolation.py`, always write a `TestCase` class with at minimum a happy-path and a permission test.
